pera1 を設計どおりに使いこなすには、3 つの考え方を押さえると後の判断が楽になります。ルートは URL の前方一致で階層を作ること、データは履歴エントリーという単位でキャッシュされること、取得と更新はローダーとアクションに分かれていることです。

## 親ルートは子の URL にもマッチする [#allow-child]

`createRouter` に渡したルートの配列は、まず詳細度の高い順に並べ替えられます。リクエストされた URL に対しては、配列の先頭から順にパターンを照合し、一致したものをすべて集めます。結果は「子から親へ」の順の配列になります。

```tsx
const routes = [
  { path: "/", component: RootLayout },
  { path: "/contacts", component: ContactsLayout },
  { path: "/contacts/:id", component: ContactPage },
];
```

URL `/contacts/42` に対しては、`/contacts/:id`、`/contacts`、`/` の 3 つがこの順でマッチします。`/contacts` のような親ルートは、インデックスルートとして宣言しない限り、その下のパスにも前方一致します。この性質がネストしたレイアウトを成立させています。

`index: true` を付けたルートは、そのパスに完全一致したときだけマッチします。一覧ページと詳細ページを同じ `/contacts` の下に置きたいときに使います。

```tsx
{ path: "/contacts", index: true, component: ContactsPage }
```

クエリー文字列とハッシュはマッチングに影響しません。`/contacts?sort=name#top` は `/contacts` と同じようにマッチします。末尾スラッシュの有無も無視されます。

## マッチした階層がそのまま画面の入れ子になる [#nesting]

`Router` はマッチした配列を親から子の順に反転し、親コンポーネントの中に子コンポーネントを入れ子にして描画します。親コンポーネントは、子を差し込みたい位置に `Outlet` を置きます。

```tsx
function RootLayout() {
  return (
    <div>
      <Header />
      <main>
        <Outlet />
      </main>
    </div>
  );
}
```

`component` を持たないルートは、親の `Outlet` の位置に子をそのまま透過させます。レイアウトを挟まずにルートを 1 段増やしたいときに便利です。

## データは履歴エントリー単位でキャッシュされる [#history-entries]

ブラウザーでページ遷移するたびに、Navigation API は履歴エントリーを 1 つ追加します。pera1 はこのエントリーごとに UUID の ID を割り当て、ローダーとアクションの実行結果を ID 単位で管理します。

同じエントリーに戻ってきたとき (ブラウザーの「戻る」など)、ローダーの結果はストアから取り出されます。再取得するかどうかは `shouldReload` が決めます。既定では、クエリー文字列が変わったときと、遷移前のルート階層に含まれていなかったルートが現れたときだけ再取得し、それ以外は前回の結果を再利用します。

履歴エントリーがセッション履歴から溢れて破棄されると、対応するデータもストアから削除されます。メモリーが際限なく増えることはありません。

## データの流れは 3 つの場面に分かれる [#data-flow]

**初回表示**では、`engine.init` が URL を照合し、マッチしたすべてのルートのローダーを並行して起動します。ローダーの完了を待つ必要はありません。画面はすぐに描画され、待機と表示は各コンポーネントに任せます。

**GET の遷移**では、`startLoaders` が遷移前後のルートを比較し、各ローダーについて再利用か再実行を判定してから、新しい状態を UI に通知します。

**フォーム送信 (POST)** では、まず送信先に最も近い親ルートのアクションが 1 つだけ実行されます。アクションが完了するとリダイレクト先が確定し、その URL のローダーが実行され、結果が画面に反映されます。データ更新後は原則として再取得が必要なため、`shouldReload` の既定値は常に `true` です。

## 非同期の結果は `NinjaPromise` で受け取る [#ninja-promise]

ローダーとアクションの結果は `NinjaPromise` という thenable で渡されます。コンポーネントでは `React.use` に渡すのが基本です。読み込み中はサスペンドして `Suspense` のフォールバックが表示され、失敗時は最も近いエラーバウンダリーが例外を受け取ります。成功すると、解決済みの値がそのまま返ります。

```tsx
function ProfilePage() {
  const user = use(useLoaderData<typeof userLoader>());
  return <Profile user={user} />;
}
```

`NinjaPromise` は通常の Promise と同じように `await` することもできます。状態を自分で確認する必要はありません。エラー表示はエラーバウンダリーに集約できるため、ローダーやアクションの中で例外を握りつぶす理由もなくなります。

## エンジンと UI バインディングは分離されている [#engine]

ルーティングの実行は `IEngine` を実装したエンジンが担当します。既定の `NavigationApiEngine` は Navigation API のイベントを購読し、`init`、`start`、`submit`、`navigate` の 4 つのメソッドで外部から操作されます。エンジンは差し替え可能です。テスト用のメモリールーターやハッシュベースのルーターを自作すれば、Navigation API のない環境でも同じように動かせます。

`createRouter` はエンジンとルート定義を仲介し、購読とスナップショットの取得を提供します。React バインディングの `Router` は `useSyncExternalStore` でこのスナップショットを購読し、必要な部分だけを再描画します。

## 現時点での制約 [#limitations]

pera1 は小さなライブラリーで、あえて持っていない機能もあります。導入前に次の点を確認してください。

| 制約 | 内容と代替手段 |
| --- | --- |
| SSR 非対応 | ブラウザー専用です。サーバーでの HTML 生成は行いません。 |
| 既定エンジンは Navigation API 必須 | `NavigationApiEngine` は未対応ブラウザーで動きません。自作エンジンに差し替えれば回避できます。 |
| 404 ページ | マッチしない場合、`Router` は `null` を描画します。`{ path: "/*", component: NotFoundPage }` のフォールバックルートを定義すると 404 相当の画面を表示できます。 |
| グローバルな進行状態 | ナビゲーション全体のローディング状態を返すフックはありません。読み込み中表示は `Suspense` のフォールバックで表現します。 |
| ルートの遅延読み込み | `React.lazy` をそのまま `component` に渡すことはできません。[コード分割](/guides/code-splitting)でラッパーを紹介しています。 |
| ルート定義の型推論 | ルート定義配列の `path` は `string` として扱われるため、ローダーの `params` は `string \| undefined` で届きます。`useParams<TPath>()` を使うとコンポーネント側で型を付けられます。[TypeScript](/guides/typescript)を参照してください。 |
